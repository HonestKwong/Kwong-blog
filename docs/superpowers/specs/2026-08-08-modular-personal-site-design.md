# 模块化个人网站设计

## 1. 目标

建设一个由 AI 长期维护的前后端一体化个人网站，包含：

- 对外公开的个人博客；
- 登录后可见的股票看板；
- 登录后可见的面试准备内容；
- 登录后可见的英语学习内容；
- 后续可按统一约定添加的新模块。

系统运行在已有的海外 Linux VPS 上，与现有 Xray、nginx 容器共存。代码推送到 GitHub `main` 分支后，由 GitHub Actions 自动测试、构建镜像并部署。部署网站不得中断 Xray 服务。

## 2. 已确认的约束

- 网站采用单用户模式，但公开博客无需登录。
- 第一阶段使用 SQLite，保留迁移到 PostgreSQL 或 MySQL 的能力。
- VPS 有 root 权限并已安装 Docker。
- 现有 443 端口由 Xray 占用；普通网站流量由 Xray fallback 到 nginx 的 Unix Domain Socket。
- nginx 与 Xray 通过共享卷中的 `/dev/shm/h1.sock` 和 `/dev/shm/h2c.sock` 通信。
- Xray 的 gRPC/XHTTP 路径必须保持可用。
- 域名购自 Namecheap，服务器在海外；该部署不依赖中国大陆 ICP 备案。
- 网站可替换当前 Cloudreve 伪装站，但用户理解真实内容可能使个人身份、域名和代理服务器产生关联。

## 3. 方案比较与选择

### 方案 A：Next.js 模块化单体 + SQLite（采用）

前端页面、服务端接口、认证和数据访问都在一个 Next.js 应用中，并按业务模块隔离。

优点：

- 只有一个应用镜像和一个部署单元；
- 前后端类型可以共享，减少接口漂移；
- React/Next.js 生态和 AI 辅助开发资料丰富；
- SQLite 无独立数据库进程，适合低并发的单用户网站；
- 博客可以服务端渲染，利于公开访问和 SEO。

代价：

- 必须通过目录边界、测试和检查规则维持模块隔离；
- SQLite 不适合未来的高并发多用户写入。

### 方案 B：Nuxt 模块化单体 + SQLite

总体能力与方案 A 接近，适合已有 Vue 技术偏好的团队。当前没有明确 Vue 偏好，且长期 AI 维护更看重生态覆盖，因此不采用。

### 方案 C：独立前端、后端和数据库服务

边界最清晰，适合多人团队和复杂扩缩容，但会增加接口版本、部署编排和故障排查成本。对于单用户网站属于过度设计，因此不采用。

## 4. 总体架构

系统采用模块化单体：

```text
浏览器
  │
  ▼
Xray :443
  │ 普通网站流量 fallback
  ▼
nginx（h1.sock / h2c.sock）
  │ HTTP，Docker 内部网络
  ▼
kwong-web:3000
  ├── 公开博客
  ├── 登录与会话
  ├── 股票看板
  ├── 面试准备
  ├── 英语学习
  └── SQLite 持久化文件
```

Next.js 应用只在 Docker 网络内监听 3000 端口，不向宿主机发布端口。80/443、证书和 Xray fallback 均由现有基础设施负责。

## 5. 代码组织与模块边界

建议目录：

```text
src/
  app/                       # Next.js 路由和布局
    (public)/                # 明确公开的路由
    (private)/               # 需要登录的路由
    api/                     # HTTP 接口入口
  core/
    auth/                    # 登录、会话、路由授权
    db/                      # ORM、迁移、备份和导出
    search/                  # 搜索接口与 SQLite 实现
    ui/                      # 设计令牌和通用 UI
    observability/           # 日志、健康检查
  modules/
    blog/
    stocks/
    interview/
    english/
```

每个业务模块包含自己的领域模型、服务、页面组件、测试和 `README.md`。模块 README 说明职责、公开接口、数据表、外部依赖和常见修改方式，作为 AI 的局部上下文。

边界规则：

1. 业务模块不能直接导入其他业务模块。
2. 跨模块共享能力必须通过 `core` 中的稳定接口提供。
3. 数据库访问集中在模块的数据访问层，不在页面或组件中散落查询。
4. 禁止业务代码直接使用数据库专属 SQL；确需使用时封装在适配器内并测试。
5. 新模块由统一模板生成，默认属于私有路由。

这些规则通过 lint 边界检查、类型检查和自动化测试执行，而不只依赖文档约定。

## 6. 功能范围

### 6.1 公开博客

- 文章列表、详情、标签和基础 SEO 元数据；
- Markdown 内容编辑与渲染；
- 草稿和已发布状态；
- 仅已发布文章允许匿名访问。

第一阶段不实现评论、公开注册和多作者协作。

### 6.2 股票看板

- 自选股和个人观察列表；
- 行情摘要、持仓备注和个人分析记录；
- 行情数据通过独立 provider 接口接入，密钥只保存在服务器环境变量中；
- 外部数据不可用时显示最近一次成功数据及更新时间。

具体行情供应商、市场范围和刷新频率在实现该模块前单独确认。第一阶段不提供自动交易能力。

### 6.3 面试准备

- 题目、答案、标签和掌握状态；
- 支持 Markdown；
- 按标签和状态筛选；
- 学习记录与复习时间。

### 6.4 英语学习

- 单词、释义、例句和学习状态；
- 学习与复习记录；
- 后续可增加间隔重复算法，但第一阶段不引入复杂推荐系统。

## 7. 认证与授权

系统只有一个管理员账号，不开放注册。

- 密码只以强密码哈希形式保存，不保存明文；
- 会话 Cookie 使用 `HttpOnly`、`Secure` 和合适的 `SameSite` 策略；
- 会话签名密钥通过服务器环境文件注入；
- 登录接口有速率限制和统一失败提示；
- 默认拒绝访问：只有明确列入公开白名单的博客页面和健康检查可以匿名访问；
- 股票、面试、英语、草稿和管理操作必须通过服务端授权检查；
- 页面隐藏不能替代服务端授权。

## 8. 数据设计与数据库迁移

第一阶段使用 SQLite，数据库文件挂载到 Docker 命名卷或宿主机专用数据目录，不写入镜像。

为了降低未来迁移成本：

1. 使用支持 SQLite、PostgreSQL 和 MySQL 的 ORM；
2. 使用数据库无关的数据类型作为核心模型；
3. 日期统一以 UTC 表达，业务层显式处理时区；
4. 布尔值、JSON、大小写比较和自增主键行为由测试覆盖；
5. 搜索通过 `SearchProvider` 接口访问，SQLite FTS5 仅存在于实现层；
6. 提供版本化的数据导出格式和导入脚本；
7. 模块代码不依赖 SQLite 特有函数或 pragma。

迁移数据库时的预期步骤为：

1. 根据 ORM schema 在目标数据库创建结构；
2. 暂停网站写入并生成一致性导出；
3. 导入数据并校验记录数、关联和抽样内容；
4. 替换搜索 provider；
5. 运行全量测试和迁移验收；
6. 切换数据库连接并保留 SQLite 只读备份。

迁移仍需要一次有计划的维护操作，但不要求重写业务模块。

## 9. 搜索

业务模块只依赖统一接口，例如：

```ts
interface SearchProvider {
  index(document: SearchDocument): Promise<void>;
  remove(id: string): Promise<void>;
  search(query: SearchQuery): Promise<SearchResult[]>;
}
```

第一阶段由 SQLite FTS5 实现。未来迁移到 PostgreSQL 时可替换为全文检索或 pgvector 组合实现，业务调用方不变。

## 10. nginx 与 Xray 集成

现有 `/trgrpc`、`/vlgrpc`、`/vmgrpc`、`/ssgrpc` 和 `/vlxh/` location 保持原样。

`h1.sock` 和 `h2c.sock` 对应 server 块中的普通 `location /` 均改为反向代理到 `kwong-web:3000`，确保 HTTP/1.1 和 HTTP/2 得到一致的网站内容。转发时设置真实 Host、客户端 IP、转发链和 HTTPS 协议信息。

网站与 nginx 必须位于同一个 Docker 网络。推荐在 `xray-deploy` 的 Compose 文件中增加网站服务，使其直接加入现有 `mynetwork`。若将来拆分为两个 Compose 项目，则把网络改为固定名称的 external network。

nginx 配置修改前执行语法检查，成功后仅 reload nginx，不重启 Xray。网站镜像的日常发布不修改或 reload nginx。

## 11. CI/CD

### 11.1 持续集成

每个 Pull Request 和 `main` 分支推送执行：

- 依赖锁定和可重复安装；
- 格式与 lint 检查；
- TypeScript 类型检查；
- 单元和集成测试；
- 生产构建；
- 容器镜像构建和基础安全扫描。

### 11.2 镜像发布

通过检查后：

- 构建多阶段、非 root 运行的生产镜像；
- 推送到 GitHub Container Registry；
- 使用不可变的 Git commit SHA 标签；
- 可额外更新 `main` 标签，但部署和回滚始终使用 SHA。

### 11.3 自动部署

`main` 成功构建后，GitHub Actions 通过专用 SSH 部署账号连接 VPS：

1. 记录当前运行镜像的 SHA；
2. 拉取新镜像；
3. 只重建 `kwong-web` 服务；
4. 等待 `/api/health` 健康检查；
5. 成功后清理过旧镜像；
6. 失败时恢复上一 SHA，并再次检查健康状态。

部署脚本不得执行整个 Compose 项目的 `down`，不得重启 Xray，不得覆盖证书或 nginx 配置。

服务器敏感配置保存在不进入 Git 的环境文件中。GitHub Secrets 至少包含部署主机、部署用户、SSH 私钥和 GHCR 拉取凭据。部署账号只获得完成网站发布所需的最小权限。

## 12. 备份与恢复

- 每日使用 SQLite 在线备份 API 或 SQLite backup 命令生成一致性备份，不直接复制正在写入的数据库文件；
- 备份同时包含用户上传内容；
- 备份加密后保存到服务器之外；
- 设置保留周期并定期清理；
- 至少提供一个可重复执行的恢复脚本；
- 定期在临时目录执行恢复验证，避免只有备份、无法恢复。

镜像不是数据备份。重新部署或回滚镜像不能覆盖持久化数据卷。

## 13. 错误处理与可观测性

- `/api/health` 检查进程和数据库基本可用性，不返回敏感信息；
- 使用结构化日志并为请求生成关联 ID；
- 用户界面显示可理解的错误，不暴露堆栈或密钥；
- 外部股票 API 失败采用超时、有限重试和缓存降级；
- Docker 配置日志轮转，避免磁盘被日志占满；
- 数据库迁移失败时停止发布，不启动使用不兼容 schema 的应用。

## 14. 测试策略

- `core/auth`：匿名、登录、过期会话和越权访问测试；
- 各模块：领域服务和数据访问层测试；
- 路由：公开博客可匿名访问，所有其他业务路由默认拒绝；
- 数据库：迁移、导出、导入和恢复测试；
- CI/CD：镜像健康检查和回滚脚本测试；
- nginx：配置语法检查，并验证普通网页路径与五个 Xray 路径不冲突；
- 最小端到端冒烟测试：登录、发布博客、访问三个私有模块。

## 15. AI 长期维护约定

仓库根目录提供面向 AI 和开发者的项目说明，至少包含：

- 架构与模块边界；
- 常用开发、测试、迁移和部署命令；
- 新建模块模板；
- 安全规则和禁止事项；
- 数据库变更流程；
- 完成定义：类型检查、测试、构建和文档均通过。

每次 AI 修改必须保持改动局部化，为行为变化补测试，并通过 Pull Request 和 CI 后才能部署。生产密钥、真实数据和数据库文件不提供给 AI，也不提交到 Git。

## 16. 分阶段实施

### 阶段一：平台地基

建立 Next.js 应用、模块边界、SQLite、认证、基础 UI、测试、Docker 镜像、健康检查和 CI。

### 阶段二：部署集成

完成 GHCR 发布、VPS 自动部署、回滚、持久化、备份，以及 `xray-deploy` 中 nginx/Compose 的一次性接入。

### 阶段三：首批业务模块

依次实现公开博客、面试准备、英语学习和股票看板。股票供应商和刷新策略在该模块开始前确认。

每个阶段均保持可独立验证和回滚，避免一次发布同时改变应用、代理和数据层。

## 17. 验收标准

- 公开博客在未登录状态下可访问，私有模块无法匿名访问；
- 网站在 HTTP/1.1 与 HTTP/2 下行为一致；
- 五个现有 Xray 路径保持工作；
- 推送到 `main` 后可自动完成测试、镜像发布和网站容器更新；
- 网站部署失败能自动恢复上一镜像，且 Xray 不被重启；
- SQLite 数据和上传内容在容器重建后仍然存在；
- 备份可以在干净目录恢复并通过数据校验；
- 新业务模块可按模板加入，且不能直接依赖其他业务模块；
- 仓库中不存在生产密钥、数据库文件或个人数据。
